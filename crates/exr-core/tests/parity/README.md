# exr-core ↔ C++ OpenEXR parity gate (scanline + tiled + deep + multipart)

This directory holds the end-to-end interop gate that proves `exr-core`'s
**scanline**, **tiled** AND **deep** (scanline + tiled) reader/writer produce and
consume the exact same bytes/pixels/samples as a real C++ OpenEXR (the vcpkg
`OpenEXR-3_4` library).

## Status

`parity_exr.rs` has **108 tests; all pass** against OpenEXR 3.4.15 (vcpkg
`x64-windows-static-release`, which links OpenJPH 0.31.0 and libdeflate 1.26).
Two codecs need a matching C++ build for byte identity:

- **DWA**: the MSVC-x64 oracle compiles OpenEXR's **SSE2** DCT bodies and runs them (AVX is
  never detected without GCC inline asm). They sum floats in a different order than the scalar
  DCT, so they are not bit-identical to it. `compressor/dwa/dct.rs` ports the SSE2 order
  op for op. A GCC/AVX or ARM oracle would produce different DWA goldens; that is expected.
- **HTJ2K**: the codestream's COM marker embeds `OpenJPH Ver X.Y.Z`, so byte identity needs
  `jph-rs` to port the exact OpenJPH version the oracle links (0.31.0).

## How to run

```
cargo xtask parity-exr
```

This (Windows + vcpkg only):

1. Applies the MSVC toolchain via `vcv-rs` (no manual `vcvars64.bat`).
2. Compiles `oracle.cpp` with `cl` (`/EHsc /std:c++17`, CRT `/MD` or `/MT` per
   triplet), linking the OpenEXR / Iex / IlmThread / Imath libraries found in the
   triplet's `lib/` (static triplets add OpenEXRCore, openjph, and libdeflate).
3. Runs the oracle to regenerate every committed golden and decode dump.
4. Runs `cargo test -p exr-core --test parity_exr` with `EXR_ORACLE_EXE` pointing
   at the oracle (and, for a DLL triplet, the vcpkg `bin/` on `PATH`).

The vcpkg tree is picked by the shared resolver in `xtask/src/vcpkg.rs`: `VCPKG_INSTALLED`
(a full `installed/<triplet>` path) wins, else the first `x64-windows*` triplet under
`$VCPKG_ROOT/installed` (default `C:/vcpkg/installed`) that has the header.

`cargo test -p exr-core` also works standalone and now runs **everything**:

* direction (a) reads the committed goldens;
* direction (b) finds `oracle.exe` here automatically when a previous
  `xtask parity-exr` built it (`EXR_ORACLE_EXE` still wins). It links vcpkg
  statically on this project's triplet, so it needs no extra `PATH`;
* if neither is available, those tests **FAIL** rather than printing SKIP and
  reporting PASSED. Set `EXR_ALLOW_SKIP=1` to opt out
  deliberately — the same variable `imath-rs` and `deflate-rs` use.

## exrheader gate (`cargo xtask parity-header`)

Builds OpenEXR's own `exrheader` (`openexr/src/bin/exrheader/main.cpp`, unmodified, same
vcpkg/MSVC flags as the oracle via `openexr_build`) to `exrheader.exe` here, then runs the ignored
`api::describe::tests::matches_exrheader`: every attribute of every part of every golden, corpus and
synthetic all-types file must print, through `Row::line`, exactly what exrheader prints (types
exrheader has no formatter for are compared as the bare `name (type t)` line).

## Committed C++ decode dumps (`golden_*.exr.dump`)

A lossy codec has no source formula to check a decode against, so the only exact
reference is what a real C++ OpenEXR reader produced from the same bytes. Committing
those decodes lets the lossy checks run without the oracle binary.

`oracle.exe dump <golden> <out>` / `dump-tiled <golden> <out>` therefore write
C++'s decode as raw planar bytes, and xtask commits one next to each lossy
golden (B44, B44A, DWAA, DWAB, PXR24 — scanline and tiled). Layout, chosen so
the Rust side can rebuild it exactly:

```
for each channel, in the file's (alphabetical) channel order:
  for y in 0..height, for x in 0..width:
    the sample, little-endian: 2 bytes for HALF, 4 for FLOAT/UINT
```

`dump-tiled` repeats that per level, levels in increasing order, each at its own
resolution. The lossless codecs get no dump: they are checked against the KNOWN
formula, which is a stronger and completely independent oracle.

## What is checked

* **Direction (a) — C++ → ours (read):** our `InputFile` reads `golden.exr`
  and we assert every pixel's bits and the header's required + custom attributes
  match the KNOWN image.
* **Direction (b) — ours → C++ (write):** our `OutputFile` writes the KNOWN
  image to a temp file; the C++ oracle reads it back and we assert C++ sees
  every pixel + header attribute exactly.
* **ours → ours** in-memory round trip (no C++ needed) as a baseline.

**Byte-exact vs pixel-exact:** the *header* (magic, version word, attribute
encoding, line-offset table) is byte-exact between our writer and C++ — this is
what makes C++ able to open our file at all. The *pixel data* is checked
bit-exact per channel (HALF = 16-bit pattern, FLOAT = 32-bit pattern) in both
directions.

## The KNOWN image (defined identically in `oracle.cpp` and `parity_exr.rs`)

* **67×43**, data/display window `[(0,0)..(66,42)]`, `NO_COMPRESSION`,
  `INCREASING_Y`.
* Channels (stored alphabetically by IlmImf): `A,B,G,R,U,Z`; `R,G,B` = HALF,
  `A,Z` = FLOAT, **`U` = UINT**.
* A **flat rectangle** `x ∈ [8,40)`, `y ∈ [8,24)` where every channel is
  constant.
* Pixel pattern with `idx = y*67 + x` (outside the flat rect):
  * `R = half(1.0  + idx*0.5)`
  * `G = half(100.0 + idx*0.25)`
  * `B = half(-50.0 + idx*1.0)`
  * `A = f32((idx%16)*0.013 + 0.25)`
  * `Z = f32(idx*4.0)`
  * `U = u32(idx*3 + 11)`
  * All HALF values use round-to-nearest-even IEEE float→half conversion, so
    the 16-bit patterns match on both sides.
* Header extras: `owner` (string) = `"exr-rs"`, `parityTag` (int) = `31337`.

### Why this size

A tiny image is a single chunk that most codecs cannot shrink, so C++ stores it
**raw** and a byte-identity test would exercise only the header and the raw-store
rule. 67×43 is multi-chunk for ZIP (16 lines), B44 (4), DWA (32) and PIZ, is not a
multiple of 4/8/16/32, and compresses. `A` and `Z` are deliberately
**low-entropy**: with a plain `A = idx*0.013` / `Z = idx*100.0` the FLOAT
channels' low mantissa bytes were effectively random, PIZ (which wavelets
16-bit words) could not beat its own Huffman table, and the tail chunk was
still stored raw. Real EXR float channels are smooth, so this is more
representative, not weaker.

**A golden can never silently degrade to raw again**: the test
`every_compressed_golden_actually_compresses` scans this directory, and
`support::assert_chunks_compressed` requires that a compressed golden shrinks in
total and that its **largest** chunk is compressed. (Not *every* chunk: a 4×32
edge tile genuinely does not shrink under PIZ, and demanding it would force
tile-aligned dimensions and lose the partial-tile coverage.)

## 3.4.15 vs 3.3.11 note

vcpkg ships **OpenEXR 3.4.15**, and it is the **behavioural target**. `exr-core` keeps the
v3.3.11 IlmImf file layout, but where 3.3.11 and 3.4.15 behave differently (OpenEXRCore
header parsing, lazy chunk tables, codec details such as `wdec14_4` or DWA `validate_size`),
the port follows 3.4.15. The on-disk format itself did not change between them. So any
mismatch this gate reports is a **real port bug**, never something to mask.

## TILED gate

The oracle also speaks `Imf::TiledOutputFile` / `Imf::TiledInputFile`:

* `oracle.exe write-tiled <path> <codec> <levelmode> [minX minY]` — writes the
  KNOWN tiled image (`mipmap`/`one`, optional off-origin data window).
* `oracle.exe read-tiled <path>` — prints tile/level metadata
  (`TILEDESC`/`LEVELMODE`/`NUMLEVELS`/`LEVEL`) + every pixel of every level
  (`TPIX <l> <chan> <x> <y> <hexbits>`, x/y relative to the level min).

### The KNOWN tiled image (defined identically in `oracle.cpp` and `parity_exr.rs`)

* **68×44, tile 32×32** → 3×2 tiles at level 0 (partial right + bottom tiles).
  Smaller tiles carry too little data for PIZ or DWAB to shrink, and would be stored raw.
* channels (alphabetical): `A,B,G,R,U,Z`; `R,G,B` = HALF, `A,Z` = FLOAT,
  `U` = UINT.
* `INCREASING_Y`, `ROUND_DOWN`; `owner`/`parityTag` extras as for scanline.
* per-pixel formula keyed on coords **relative to the level data window**
  `(px, py)` + a per-level bias `lvlbias = lx*7 + ly*13`:
  `tidx = py*levelWidth + px`;
  `R = half(1.0+(tidx+lvlbias)*0.5)`, `G = half(100.0+tidx*0.25+lvlbias)`,
  `B = half(-50.0+tidx*1.0-lvlbias)`, `A = f32(((tidx+lvlbias)%16)*0.013+0.25)`,
  `Z = f32((tidx+lvlbias)*4.0)`, `U = u32(tidx*3+lvlbias+11)`
  (relative ⇒ identical on/off-origin).
* An **off-origin** variant uses data window min = `(11,7)` to exercise the
  tile-rectangle seam end-to-end vs C++.

### Committed tiled goldens

`golden_tiled_<codec>_<levelmode>[_variant].exr`:
NONE/RLE/ZIP/ZIPS/PIZ + B44/B44A/PXR24/DWAA/DWAB at `one`; NONE/ZIP/PIZ at
`mipmap` (all levels); plus `none_one_offset` (off-origin data window),
`zip_mipmap_roundup` (**ROUND_UP** level rounding), `zip_one_randomy`
(**RANDOM_Y** tile order) and `zip_one_decreasing` (**DECREASING_Y**). The last
three check that our reader derives the right level sizes under ROUND_UP and reads
files whose tiles are not stored in increasing-Y order. The KNOWN formula is keyed by
pixel position, so it is a valid oracle for a RANDOM_Y file by construction.

`oracle.exe write-tiled <path> <codec> <levelmode> [minX minY] [round=up]
[order=random|decreasing]` — the trailing `key=value` options keep the
positional form stable while varying one header field.

Like the scanline goldens they are committed so
`cargo test -p exr-core --test parity_exr` runs direction (a) standalone.

### What is checked (tiled)

* **(a) C++ → ours:** our `TiledInputFile` reads each golden, every level's
  every pixel — **bit-exact** vs the KNOWN formula for the lossless codecs
  (NONE/RLE/ZIP/ZIPS/PIZ, ONE_LEVEL + MIPMAP all levels). For the lossy codecs
  (B44/B44A/PXR24/DWAA/DWAB) the STRONG check is exact **cross-decode equality**
  — our decode of the golden == the C++ oracle's decode of the same on-disk
  bytes (oracle present); standalone it asserts the full decoded pixel set.
* **(b) ours → C++:** our `TiledOutputFile` writes the KNOWN image; the oracle
  `read-tiled` reads it back and we assert tile/level metadata + every pixel —
  bit-exact (lossless) / C++-decode-of-ours == C++-decode-of-golden (lossy).

## DEEP gate

The oracle also speaks `Imf::DeepScanLineOutputFile`/`InputFile` and
`Imf::DeepTiledOutputFile`/`InputFile` (via `Imf::DeepFrameBuffer` +
`Imf::DeepSlice`, the C++ two-pass count-then-data deep API):

* `oracle.exe write-deep-scanline <path> <codec> [minX minY]` — writes the
  KNOWN deep scanline image (optional off-origin data window).
* `oracle.exe read-deep-scanline <path>` — prints `COUNT <x> <y> <n>` +
  `SAMP <chan> <x> <y> <i> <hexbits>` (x/y relative to dw.min).
* `oracle.exe write-deep-tiled <path> <codec> <levelmode>` /
  `read-deep-tiled <path>` — same for deep tiled (`DCOUNT`/`DSAMP` + the
  `TILEDESC`/`LEVELMODE`/`NUMLEVELS`/`LEVEL` metadata).

### The KNOWN deep image (defined identically in `oracle.cpp` and `parity_exr.rs`)

* **8×6** (deep tile **4×4** → 2×2 tiles); channels (alphabetical) `B,G,R` =
  HALF, `Z` = FLOAT. `INCREASING_Y`; `owner`/`parityTag` extras as elsewhere.
* **VARIABLE per-pixel sample counts** `N(x,y) = (lx + ly) % 4` (level-relative
  coords; 0,1,2,3 incl. **zero-sample** pixels).
* per-SAMPLE formula keyed on the level-relative pixel index `pidx =
  ly*levelWidth + lx` and sample index `s ∈ [0, N)`:
  `R = half(1.0+pidx*0.5+s)`, `G = half(100.0+pidx*0.25+s*2)`,
  `B = half(-50.0+pidx-s)`, `Z = f32(pidx*100.0+s)`.
* an **off-origin** scanline variant uses data window min `(-3, 7)` (level-
  relative ⇒ on-disk bytes identical to the origin variant).

### Committed deep goldens

`golden_deep_scanline_<codec>.exr` (+ `_offset`),
`golden_deep_tiled_<codec>_one.exr` and `golden_deep_tiled_<codec>_mipmap.exr`
(MIPMAP, all levels) for the valid DEEP codecs **NONE/RLE/ZIPS**
(deep is NOT ZIP/PIZ/B44/PXR24/DWA/HTJ2K — see `Compression::is_valid_deep`;
16-line ZIP is not deep-valid, only single-line ZIPS). Committed like the other
goldens so direction (a) runs standalone.

### What is checked (deep — all-lossless, so EVERYTHING is bit-exact)

* **(a) C++ → ours:** our `DeepScanLineInputFile`/`DeepTiledInputFile` read each
  golden two-pass (`read_pixel_sample_counts` → `read_pixels`/`read_tiles`);
  assert per-pixel **COUNTS exact** AND **every sample bit-exact** vs the KNOWN
  formula. Covers scanline (NONE/RLE/ZIPS, origin + off-origin) + tiled
  **ONE_LEVEL and MIPMAP (all levels)**.
* **(b) ours → C++:** our writers write the KNOWN image; the oracle
  `read-deep-*` reads it back; assert C++ sees every count + sample + metadata
  exactly — **ONE_LEVEL and MIPMAP (every level)**. Needs the oracle (see "How to run").

### Deep tiled MIPMAP — how the whole-window flat-heap is cross-checked per level

Our deep flat-heap is a safe-Rust adaptation of C++'s `char**`: it is addressed
in **whole-(level-0)-window** raster order for **every** level (`samples_before
_pixel` is always called with the level-0 window bounds). The MIPMAP gate honours that contract
while still cross-checking each level against a genuine per-level C++ KNOWN
image: for level `l` the test builds a **DW-wide** (level-0 stride) sample-count
buffer that carries the level's counts ONLY in its `lw × lh` top-left corner
(every cell outside the level rect is zero), paired with a **level-LOCAL** sample
heap (`deep_sample_heap(lw, lh)`). Because the out-of-level cells are zero,
`samples_before_pixel(lx, ly, 0, DW-1, 0)` collapses to the level-LOCAL
cumulative count, so the whole-window addressing and the per-level
`pidx = ly*lw + lx` KNOWN formula coincide exactly (helper
`deep_count_buffer_mip` in `parity_exr.rs`). Both directions iterate the real
`num_levels()` / `data_window_for_level()` from our reader/writer and the
oracle's per-level `do_write_deep_tiled`/`do_read_deep_tiled` loop, asserting
every level's counts + samples bit-exact (DW=8,DH=6,tile 4 ⇒ levels 8×6, 4×3,
2×1, 1×1). Deep MIPMAP read/write is ALSO covered (count+sample-exact, ALL
levels) by the **in-crate round-trip tests**; the tiling level math is
additionally C++-verified by the NON-deep tiled MIPMAP gate.

## MULTIPART gate

The oracle also speaks `Imf::MultiPartOutputFile` / `Imf::MultiPartInputFile`
plus the typed per-part wrappers (`Imf::OutputPart` / `TiledOutputPart` /
`DeepScanLineOutputPart` and their `*InputPart` counterparts):

* `oracle.exe write-multipart <path>` — writes the KNOWN multipart file (ONE
  file, THREE mixed-type parts) via `MultiPartOutputFile` + the `*OutputPart`
  wrappers.
* `oracle.exe read-multipart <path>` — reads with `MultiPartInputFile` + the
  `*InputPart` wrappers; prints `NUMPARTS`, `PART <p> <name> <type>`,
  `PATTR`/`PCHAN`, then `FPIX` (flat parts) or `DCNT`/`DSMP` (deep part), all
  machine-readably.

### The KNOWN multipart image (defined identically in `oracle.cpp` and `parity_exr.rs`)

ONE file with THREE parts of MIXED types — all LOSSLESS codecs, so every
pixel/count/sample is bit-exact in both directions:

| part | type          | codec | name    |
|------|---------------|-------|---------|
| 0    | scanlineimage | NONE  | `rgba`  |
| 1    | tiledimage    | ZIP   | `tiled` |
| 2    | deepscanline  | ZIPS  | `deep`  |

* Common geometry `MPW × MPH = 8 × 6` at origin, `INCREASING_Y`; the tiled part
  uses a `4×4` ONE_LEVEL/ROUND_DOWN tile → `2×2` tiles (partial bottom row).
* Channels (stored alphabetically `B,G,R,Z`): R,G,B = HALF, Z = FLOAT on every
  part; the deep part has VARIABLE per-pixel counts `N(x,y) = (x+y) % 4`.
* Flat per-pixel formula (`idx = y*MPW + x`, per-part bias `pbias = part*1000`):
  `R = half(1.0+(idx+pbias)*0.5)`, `G = half(100.0+idx*0.25+pbias)`,
  `B = half(-50.0+idx*1.0-pbias)`, `Z = f32(idx*100.0+pbias)`.
* Deep per-sample formula (`idx`, `s ∈ [0,N)`):
  `R = half(1.0+idx*0.5+s)`, `G = half(100.0+idx*0.25+s*2)`,
  `B = half(-50.0+idx*1.0-s)`, `Z = f32(idx*100.0+s)`.
* Header extras on EVERY part: `owner`(string)=`"exr-rs"`, `parityTag`(int)=`31337`.

Our deep frame buffer addresses, **per channel**, a flat contiguous sample heap
(`base_offset + samples_before_pixel(x,y)*sampleStride + i*sampleStride`), so the
test concatenates the four channel sub-heaps `[R][G][B][Z]` and points each
`DeepSlice.base_offset` at its sub-heap start (`sample_stride` = element size).

### Committed multipart golden

`golden_multipart.exr` — the 3-part mixed file written by genuine C++ OpenEXR,
committed so direction (a) runs standalone.

### What is checked (multipart — all-lossless, so EVERYTHING is bit-exact)

* **(a) C++ → ours:** our `MultiPartInputFile` + the `*InputPart` wrappers read
  `golden_multipart.exr`; assert `numParts`, each part's `type`/`name`/`owner`/
  `parityTag`, and every pixel (flat parts) / count + sample (deep part)
  bit-exact vs the KNOWN formula.
* **(b) ours → C++:** our `MultiPartOutputFile` + the `*OutputPart` wrappers
  write the KNOWN file; the oracle `read-multipart` reads it; assert C++ sees
  `numParts` + every part's metadata + pixels/counts/samples exactly. Needs the
  oracle (see "How to run").
* **ours → ours** in-memory multipart round trip (no C++ needed) as a baseline.
